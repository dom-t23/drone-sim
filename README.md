# Drone Sim

A self-flying racing drone in the browser. A quadrotor flies itself around a procedurally generated gate course, with a chase camera, an onboard FPV view, lap timing and a light trail.

**Live demo:** https://dom-t23.github.io/drone-sim/

This is an experiment in what Claude can build on its own. A scheduled Claude run picks up the project three nights a week (Monday, Thursday and Saturday), adds the next feature from `ROADMAP.md` or an idea of its own, tests it, and pushes. GitHub Pages redeploys the demo automatically. `CHANGELOG.md` shows what each night added.

## Controls

| Control | Action |
|---|---|
| **Camera** (or `C`) | Chase → orbit → onboard → **TV** (an automatic director with trackside cameras and slow-motion replays) |
| **Speed** | Simulation time 1× / 2× / 4× |
| **Pilot** (or `P`) | Racing line → original axis pursuit → **you** (race the autopilot) |
| **Field** (or `F`) | Solo → a three-lap race for a field of five or six drones with different autopilots, a live timing tower and a results card |
| **Course** (or `D`) | Difficulty: easy → normal → hard → **pro** (a split-S: it flies upside down over a two-storey gate tower) |
| **Nav** (or `V`) | Ground truth → vision → vision + IMU → map only |
| **Eyes** (or `E`) | With a camera: the modelled corner detector ↔ **pixels** (the drone finds gates in its own rendered camera picture) |
| **Blackout** (or `B`) | With a camera (vision or vision + IMU): cut it for 4 seconds |
| **Learn** (or `K`) | With the racing line on ground truth, flying solo: it learns from every lap (iterative learning control), flies its line tighter, then pushes harder |
| **Wind** (or `W`) | Off → breezy → gusty |
| **Telemetry** (or `T`) | Live charts and gate splits |
| **Ghost** (or `G`) | Show or hide the gold ghost of the best lap |
| **Night** (or `L`) | Day ↔ night: LED-lit gates, stars and a headlight |
| **Sound** (or `M`) | Motor sound and race cues on or off |
| **New course** (or `N`) | Generate a new gate layout |
| **Share** | Copy a link to this exact course |
| **What's new** (under the title, or `?`) | The intro: quick starts and what the latest overnight builds added |

**Flying it yourself** (Pilot: you): `W`/`↑` speed, `A` `D`/`←` `→` turn, `Space`/`Shift` (or `E`/`Q`) climb and descend. On phones, on-screen sticks appear (left: speed and turn; right: climb and drift); gamepads work too. You race the racing-line autopilot, shown as a cyan ghost, and your own best lap on that course, shown as a gold ghost (kept in your browser).

A plain visit opens with an intro card: four quick starts and the latest build's notes, read live from `CHANGELOG.md`. It shows once per build; shared links skip it.

The course is in the URL, e.g. https://dom-t23.github.io/drone-sim/#seed=12&d=hard (`d=pro` for a pro course with a split-S; add `&nav=vision` for vision mode, `&nav=vio` for vision + IMU, `&eyes=px` to see in pixels, `&wind=gusty` for wind, `&pilot=manual` to race it yourself, `&field=1` for a multi-drone race, `&night=1` for night mode, `&cam=tv` for TV mode, `&learn=1` to watch it learn), so any layout can be shared or revisited.

## How it works

- `src/sim.js` is the simulation core with no rendering dependencies: course generation (four difficulties; hard adds big climbs, angled gates and dive gates, pro an out-and-back course ending in a split-S tower), quadrotor dynamics (thrust vector with tilt and thrust limits, first-order lag, drag), the racing-line planner, both autopilots, the assisted manual pilot, gate/lap detection, collisions with gate frames, legs and pillars (crash, tumble and respawn), vision mode (camera model, PnP, gating and fusion, in-flight re-planning, data association for the pixel camera) and visual-inertial navigation (a simulated accelerometer and an EKF that estimates the drone and the gates together).
- `src/eye.js` is the pixel camera, also with no DOM: a small software renderer that draws the onboard view (320×180, with a depth buffer and sensor noise), and a gate detector that finds orange quads in those pixels, takes overlapping gates apart and matches quads to gates.
- `src/main.js` renders it with three.js and runs the sim at a fixed 120 Hz timestep; `src/telemetry.js` draws the telemetry panel, `src/splits.js` works out gate splits, `src/race.js` the gap to the rival when you race it, `src/field.js` the multi-drone roster, timing tower, chequered flag and results, `src/ghost.js` records the best lap and replays it, `src/director.js` places the TV cameras and directs the shots and replays, `src/learn.js` makes the Learn panel's numbers and chart, `src/fx.js` holds the rotor physics behind the prop wash and motor sound, and `src/audio.js` synthesises the sound with Web Audio, and `src/intro.js` (content) with `src/landing.js` (DOM) make the intro card and build badge from the changelog.
- `test/` holds headless checks run with `npm test` (Node 18+). They fly a set of course seeds on every difficulty and nav mode and fail if the drone misses gates, crashes, strays from its line, gets slower, mis-estimates gates, or the state goes non-finite.

The default autopilot flies a **racing line**: a smooth closed spline through every gate, crossing each one square-on. Where it crosses each opening (up to 0.6 m off centre) and how hard it swings in are tuned by coordinate descent on the planned lap time. Each point on it gets the fastest speed whose turn still fits the drone's tilt and thrust limits, then forward and backward passes add acceleration and braking, using only what the turn leaves of that envelope (a friction circle), so it brakes early for corners over a crest. The tracker feeds forward the acceleration the path needs (turning, speeding up, beating drag) and corrects any position and velocity error with PD feedback. The line on the course shows the plan, coloured blue (slow) to orange (fast).

**Pro courses and the split-S** (the **Course** button, or `d=pro`). Pro is an out-and-back course: out along one side, climbing, round a two-gate hairpin, back low along the other side, and each lap ends at a two-storey tower of gates. The drone goes through the top gate, rolls upside down, pulls through a half loop and comes back out through the gate directly beneath, heading the other way. That is a real acro manoeuvre: over the top it points its thrust *downwards*, adding to gravity to pull the loop tight, which no amount of tilting the right way up can do. Everywhere else the planner keeps the drone within 55° of upright; between the tower's two gates it lets the thrust point any way at all and only limits how hard it pushes, so the speed profile plans for flying inverted. The attitude follows a pilot's split-S: a half roll about the nose (at about 1000°/s) as it goes through the top gate, then the body pitches round with the thrust until it is upright again, heading back. The drone, its onboard camera and its accelerometer all use that attitude, and ghosts and TV replays record it. In TV mode the director replays each split-S in slow motion.

**Vision mode** (the **Nav** button) takes away the drone's perfect knowledge. Its map has every gate moved up to 2.6 m, so flying the map alone (**map only**) misses gates. With **vision**, a synthetic onboard camera finds the corners of the real gates in view, with pixel noise, lost corners and the odd wild one. Each detection is turned into a gate position by PnP (fitting the gate's known shape to the corners by Levenberg-Marquardt). It's checked against what the drone already believes (innovation gating, which throws out the wild ones) and fused into a running estimate. The racing line is re-planned through the corrected gates as it flies. The cyan frames show where the drone believes each gate is, and the onboard view shows the detections: green when used, red when rejected.

**Eyes: pixels** (the **Eyes** button, with vision or vision + IMU) replaces the modelled corner detector with real pixels. Every camera frame, the sim draws the 320×180 colour picture the onboard camera would see: sky, a textured ground, the gate frames in orange with their depth and shading, legs and pillars, with a depth buffer so things hide each other, plus sensor noise. The detector only gets that picture. It picks out the orange pixels, groups them into blobs, fits a quadrilateral to each blob's outline and refines each side with a line fit to sub-pixel corners, then checks it really is a gate frame (a ring with solid, straight sides). Gates often line up one behind another, so a near and a far frame can merge into one blob; then it slides the outline it expects to see over the blob to take the near gate out. It is never told which gate is which: it matches each quad to the gate it expects there, mostly by size (a map error moves a gate sideways but hardly changes how far away it is), and leaves out anything ambiguous. The inset (bottom right) shows the drone's actual picture: green quads were fused, dashed cyan outlines are where its map said the gates would be. It sees less far than the model (gates are found out to about 35 m), so it crosses gates it isn't yet sure of at their believed centre, but it races as fast as with the model once it has seen the course, and flies all but a few per cent of hard courses cleanly.

**Vision + IMU** goes one step further: the drone doesn't know where *it* is either. All it has is the camera and an accelerometer with noise and an unknown bias, so integrating the accelerometer alone drifts metres off within a lap. An extended Kalman filter holds the drone's position, velocity and accelerometer bias together with every gate's position in one state (EKF-SLAM), so each gate the camera sees corrects the drone and the map at once. It finds the bias in a second on the start pad (zero-velocity updates), then races within about 0.2 m of where it really is, and within a few centimetres relative to the gate it's about to fly through. In the chase view, the magenta wire ball is where the drone thinks it is (two sigma in radius) and the red ball is where the accelerometer alone would put it since the start of the lap. Open **Telemetry** for the position error against the filter's own 2σ bound.

**Camera blackout** (the **Blackout** button, shown whenever the drone you're watching has a camera) cuts the camera for 4 seconds. The drone knows what it doesn't know: it keeps racing through gates it has already pinned down (to within 0.2 m, relative to itself), but for a gate it hasn't, it plans a stop 8 m short, hovers, turns to look where it thinks the gate is, and goes once the camera finds it. With vision + IMU it is also flying on the accelerometer alone, so its own uncertainty (the magenta ball) grows until even known gates are in doubt, then snaps back with the first gate it sees.

**Learn** (the **Learn** button) lets the racing pilot learn from its own laps. It flies the same line every lap, so its tracking errors repeat: the same lag into the same corner, the same drift over the same crest. **Iterative learning control** turns that into a correction: after each lap, at every point of the line, it adds part of the push its feedback loop had to make there (from slightly further along, since a command shows up as position a moment later), smooths it along the line so it can't amplify noise, and holds still where the airframe was already at its limits. Within a few laps it flies its planned line three to twenty times more accurately (typically 30 to 45 cm off it on the first lap, 2 to 12 cm after a dozen). Then it cashes that in: every clean, accurate lap steps its confidence up, which hands the planner more of the thrust and tilt envelope and lets the line cross gates nearer the frame; a sloppy lap steps it down, and a crash backs it off at once and caps it below that level for good. The Learn panel charts lap time against lap 1 and the tracking error lap by lap, and the cyan ticks along the line are the learned push.

**Wind** pushes the drone through drag on its air-relative velocity: a steady wind plus random gusts. A disturbance observer compares the acceleration the drone gets with what its still-air model predicted, and cancels the difference. The planner also keeps back enough thrust for the forecast wind.

**Manual flight** works like a camera drone's velocity mode: the sticks ask for a forward speed, turn rate, climb rate and sideways drift, and the same thrust-vector loop delivers them within the airframe's limits. The turn rate is capped by speed so the drone follows its nose, and with the climb stick centred it eases to the next gate's height.

**Crashes**: gates, their legs and the scenery pillars are solid. A real hit cuts the motors and the drone tumbles to the ground, then respawns on the line just past the last gate it passed; a light touch just slides it along. Map-only mode is a ghost run and flies through frames.

**TV mode** (Camera: TV) films the race like a broadcast. When it starts, it puts a camera post beside every gate: of about 90 candidate spots per gate, the one that stands clear of every frame, leg, pillar and the racing line and can see the most of the line through that gate (line of sight is ray-cast against the same boxes the pixel camera draws). A director then cuts every few seconds between those trackside cameras (a long lens that pans with the drone and zooms to keep it the same size), low flybys, a chase cam, a heli cam and the onboard camera. It picks who to film by interest (close battles first, then the leader; a crash jumps the queue) and prefers a trackside camera the drone is flying towards, always with a clear view, cutting away if a frame or pillar gets in the way. A crash, a change of lead or the chequered flag pauses the race for a slow-motion replay from the best-placed camera, drawn from a 12-second buffer of every drone's pose. Tap a name in the timing tower to keep the cameras on that drone. The logic is in `src/director.js`, with no DOM.

**Ghost replay**: every lap is recorded (position, heading and tilt 20 times a second, plus the time at each gate), and the fastest one so far flies again as a translucent gold drone, in step with your current lap. The **Ghost** row in the stats shows how far ahead or behind it you were at the last gate. Your own best ghost is saved per course, difficulty and wind in this browser, so it is waiting for you next time.

**Multi-drone races** (the **Field** button): the drone you watch takes pole and the rest of the field lines up abreast beside it. Every entrant is the same airframe on the same course in the same wind; only the autopilot differs. **Racing line** (red) flies the optimised line, **Vision** (blue) flies it but has to find the gates with its camera, **Smooth** (teal) flies an unshaped line with gentler acceleration and braking, **Steady** (purple) only uses 60% of the envelope in turns, and **Pursuit** (white) is the original gate-axis chaser. A timing tower ranks them like F1 timing loops: whoever has passed more gates, then whoever got there first, with the gap to the leader at the last gate, lapped drones, and the fastest lap in purple. Tap a name to follow that drone with the chase and onboard cameras. With **Pilot: you** you race the whole field. Races are three laps: when the winner takes the chequered flag, everyone else finishes the next time they cross the line, and a results card shows the classification, times, gaps and best laps, with buttons to race again or move to the next course.

**Racecraft and contact**: the drones are solid to each other. Each autopilot sees the others and looks ahead (1.2 s) for anyone it's about to meet: it steps its line sideways to pass, squeezing the move back in before every gate so it never costs a frame, and if a slower drone is still in the way it holds back like adaptive cruise control until there's room. The slow Pursuit drone moves aside for the leaders as they lap it. If two drones do touch they bounce off each other (and the accelerometer of a vision + IMU drone feels the jolt); a hit faster than 6 m/s takes both out, with a tumble and a respawn.

**Night mode** (the **Night** button) turns the gates into LED gates: blue when waiting, orange for the next one (which also lights its surroundings), green once passed, each with a soft glow and a pool of light on the ground. The watched drone carries a headlight. **Prop wash** is drawn in both modes: air leaves the props at the induced velocity from momentum theory (about 7 m/s at hover), and near the ground it spreads out into a ring of dust. The **Sound** button adds a synthesised motor whine whose pitch follows rotor speed, plus rushing air, gate blips and a crash crunch.

The original autopilot, still available with the **Pilot** button, is pure pursuit along each gate's axis: the drone chases a point sliding along the line through the gate centre, so it lines up and flies straight through, slowing for sharp turns. If it predicts it would cross a gate off the opening, it swings wide and comes round for another try.

```bash
python3 -m http.server 8000   # then open http://localhost:8000
npm test                      # simulation checks, no install needed
```
